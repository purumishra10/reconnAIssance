## 2. Problem statement

A merchant using Razorpay receives money through many channels and touchpoints — customer payments, refunds, partial settlements — and this money passes through several independent records before it is confirmed as "received": the merchant's own sales ledger, Razorpay's settlement reports, and the merchant's bank statement. These three records almost never match perfectly on their own, because of timing lags, deducted fees, partial refunds, human data-entry error, and formatting inconsistencies between systems.

Today, a finance/ops person manually opens two or three spreadsheets, eyeballs rows, and tries to pair them up by hand. This is slow, error-prone, and does not scale as transaction volume grows. It is also one of the least-loved jobs in any finance team.

> [!NOTE]
> **Learning Note**: this manual process is called "reconciliation" or "recon" in finance teams everywhere, not just at Razorpay-powered merchants — the same pattern exists at every company that takes in money through more than one system.

## 3. Goals

- Automatically reconcile transaction records across three independent sources for a simulated D2C e-commerce merchant.
- Correctly classify each transaction as matched or an exception, with a stated, inspectable reason for the classification.
- Report honest, measured accuracy (match rate, precision, recall) against a held-out test batch that was not used while building or tuning the system.
- Process a batch of realistic size (target: 2,000+ synthetic transactions) within a demonstrable time budget, and report that throughput number.
- Provide a queryable audit trail — for any match or exception, show why the system decided what it decided.
- (Stretch) Let a user ask the system natural-language questions about settlements ("why did we only receive ₹48,230 this week instead of ₹50,000?") and get a correct, explainable answer — the Settlement Q&A agent.

## 4. Non-goals / out of scope

- Connecting to a real Razorpay account or real merchant data — everything runs on synthetic data generated by us (see the data model doc for the noise/messiness we inject deliberately).
- Full double-entry bookkeeping or GAAP/Ind-AS accounting compliance — we are solving the matching/detection problem, not building an accounting system.
- Tax filing or GST return generation — the tax-line-matcher direction from the track is explicitly out of scope for this build; we are focused on the reconciliation direction only.
- Multi-tenant/production security hardening, auth, or billing — this is a hackathon demo, not a shippable SaaS product (see the tech stack doc for what corners we knowingly cut and why).
- Real-time/streaming reconciliation — we process in batches, not as each transaction happens.

## 5. Users / personas

#### Primary: merchant finance/ops analyst

The person who currently does this reconciliation by hand every week. They care about: how much manual chasing is left after the tool runs, whether they can trust a "matched" verdict without re-checking it themselves, and whether the tool explains its exceptions clearly enough to act on them immediately.

#### Secondary: hackathon judges

People evaluating whether this is a credible, working finance tool versus a demo that only looks good on the happy path. They will look for: honest metrics (not cherry-picked), a real held-out evaluation, sensible handling of a genuinely messy case shown live, and a grasp of why the messiness happens (fees, timing, partial refunds) rather than a naive equality check.

## 6. Functional requirements

| ID | Requirement | Priority |
| --- | --- | --- |
| FR-1 | Ingest three synthetic data sources: internal sales ledger, Razorpay settlement report, bank statement. | Must |
| FR-2 | Run a three-tier matching pipeline: exact match, then fuzzy match, then AI-assisted match on remaining ambiguous rows. | Must |
| FR-3 | Classify every row as Matched or Exception; every Exception carries a machine-generated reason. | Must |
| FR-4 | Compute and display match rate, precision, recall, and throughput on a held-out batch. | Must |
| FR-5 | Persist a per-decision audit log (what was compared, which tier matched it, confidence, reasoning). | Must |
| FR-6 | Dashboard showing summary metrics, a matched-pairs table, and an exceptions table with filters. | Must |
| FR-7 | Settlement Q&A agent: answer natural-language questions about settlement shortfalls using the reconciled data. | Should |
| FR-8 | Re-runnable, deterministic synthetic data generator so judges can regenerate and verify results. | Should |
| FR-9 | Exportable exception list (CSV) for a finance analyst to action outside the tool. | Could |

## 7. Non-functional requirements

| Category | Requirement |
| --- | --- |
| Accuracy | Match rate ≥ 90% on the held-out batch is the internal target; the real number, whatever it is, gets reported honestly. |
| Throughput | Process at least 2,000 synthetic records end-to-end (all three tiers) in under 60 seconds on a laptop. |
| Explainability | Every automated decision (match or exception) must have a human-readable reason retrievable via the API and shown in the UI. |
| Cost control | The AI-assisted tier (LLM calls) must only be invoked on the minority of rows that exact and fuzzy matching could not resolve — not on every row. |
| Reproducibility | Same synthetic data seed produces the same dataset and, given the same code, the same evaluation numbers. |
| Demo resilience | The system must run fully offline from cached/pre-computed results as a fallback in case live LLM calls fail during the demo. |

## 8. Success metrics — "the bar" for this track

The hackathon brief for Track 04 states the bar explicitly: "Throughput plus measured accuracy plus an honest exception list. One cherry-picked match proves nothing." We treat this as literal acceptance criteria:

- Throughput: a stated records/second number, measured on the full batch, not a curated subset.
- Measured accuracy: precision, recall, and match rate computed against a held-out set the matching logic was never tuned against.
- Honest exception list: the demo explicitly shows unresolved exceptions and explains why they could not be resolved — not just the clean matches.

## 9. Assumptions

- Merchant type: a mid-size D2C e-commerce business processing online card, UPI, and netbanking payments through Razorpay.
- Settlement cadence: T+2 days, batched (many orders settle together in one bank credit) — the real-world default for many Razorpay merchants.
- Data volume: a few thousand transactions is a realistic "one month" batch for a mid-size D2C merchant, which is why that is our throughput target.
- LLM access: an Anthropic Claude API key is available for the AI-assisted matching tier and the Q&A agent (see the tech stack doc for the specific model and fallback plan).

## 10. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Synthetic data looks too clean / unrealistic to judges | Undermines credibility of the whole demo | Base noise patterns on real reconciliation failure modes (see data model doc §2) and have a domain-savvy reviewer sanity-check them |
| LLM tier is slow or fails live during demo | Demo breaks or stalls | Pre-compute and cache one full run; demo primarily from cached results, with a small live re-run as a bonus |
| Match logic overfits to the data we hand-tuned on | Reported accuracy is not credible | Strict held-out split enforced in code, never touched until final scoring (see architecture decision doc, ADR-003) |
| Scope creep into full accounting/tax territory | Runs out of time before polishing the core demo | This scope doc is the source of truth — anything not listed under Functional Requirements is out unless explicitly added here first |

- A documented, reproducible synthetic dataset and generator.
